# DESCENT

A downhill bike racing game with a hand-drawn, cel-shaded look. Four riders race from a
mountain summit down to the valley floor. Built with Three.js and TypeScript.

**Everything in this game is made by code - nothing is downloaded.** No pre-made 3D
models, no image textures, no background photos, no fonts, no sound files. Every
character and object is built from basic shapes in code. Every texture is drawn using
code (like a program drawing on a canvas). Every sound effect is generated by code, not
recorded. Even the mountain itself is generated using math (noise patterns) and then
"eroded" by simulation, the same way wind and water shape a real mountain over time.
Even the text in the game's menus is drawn as shapes, not using a font file.

```bash
npm install
npm run dev
```

That's it. Run those two commands, open the link it gives you, and you're playing.

## Controls

| Key | Action |
|---|---|
| **W** / **↑** | Pedal |
| **A** **D** / **←** **→** | Steer |
| **S** / **↓** | Rear brake - locks the back wheel, slows you down fast, kicks up dirt |
| **Q** | Front brake |
| **Space** | Crouch down to load up energy. Hold it going into a ramp and let go right at the top for extra height. Also lets you hop on flat ground. |
| **J** / **K** | Lean back / lean forward. Leaning back on flat ground lets you "manual" (ride on the back wheel) |
| **Shift** + direction | Trick 1 (tailwhip, x-up) |
| **E** + direction | Trick 2 (superman, tabletop) |
| **F** | Boost - uses up meter you build by doing tricks |
| **R** | Restart from your last checkpoint |
| **C** | Look behind you |
| **V** | Switch camera angle |
| **Esc** | Pause |
| **`** | Show performance stats |

A regular game controller also works, and it feels a bit more responsive than the keyboard.

**The main skill to learn:** timing your crouch. Crouch down as you approach a ramp, then
release right as you hit the lip - do it right and you'll launch much higher than the
ramp alone would send you. Do it too early and you'll barely get any height. You have
about 140 milliseconds to get the timing right, and mastering this is basically the whole
skill ceiling of the game.

## Art style

The whole game uses one fixed look: **golden sunrise in the mountains**. Sunlight comes in
low at a 21.5° angle from the east-southeast, shadows are cool purple-grey, and distant
mountain ridges fade into flat, stacked layers of hazy blue-green, like a painting, not a
photo.

Every color used in the game is defined in one place: `src/npr/Palette.ts`. Nothing is
color-picked randomly elsewhere in the code.

Three rules are actually built into the code (not just followed by habit):

1. **No realistic lighting/materials are possible.** The code has no way to create
   realistic reflective surfaces, that type of material doesn't exist anywhere in this
   project. Every surface uses a flat "cartoon" material instead.
2. **Shadows use color, not just darkness.** Instead of just making a surface darker in
   shadow, the game shifts its color toward purple and desaturates it. That's the biggest
   reason this looks like a hand-painted cartoon instead of a simple toon-shaded game.
3. **Nothing fades smoothly.** Lighting, shine, fog, sky color, even fake reflections,
   all of it changes in hard steps/bands instead of smooth gradients, on purpose.

### How the visual style is built (technical pipeline)

```
 shadow setup  ->  scene data pass  ->  outlines around objects  ->  main cartoon shading
                                                                          |
   final image  <-  color correction  <-  glow effect  <-  speed lines  <-  inner detail lines
```

**Banded lighting** - Instead of smooth light-to-dark shading, each material has 3-4
distinct light/dark "bands," and each material type (rock, dirt, plants, skin, clothing,
metal, glass, wet rock) has its own custom look. The edges between bands are smoothed out
based on the camera's viewing angle, which is what keeps those edges from crawling weirdly
around the screen as the camera moves, a common problem in simpler toon-shading setups.

**Two separate systems draw the outlines:**

- *Outline shells* around riders, bikes, rocks, and trees, basically an inverted copy of
  each object pushed slightly outward, using smoothed corner directions everywhere shapes
  need outlines. This smoothing step prevents visible gaps or tears in the outline at
  corners, which is a very common flaw in this style of rendering when skipped. The
  outline gets thinner or thicker automatically depending on how close the camera is, so
  it looks consistent whether something is 3 meters or 300 meters away.
- *Screen-space edge detection* catches details outline shells can't, like a crease
  within a single shape, or where an arm crosses in front of a body at the same distance
  from camera, or the line between a tire and its rim.

These two systems are balanced so they don't overlap and create a thick, muddy black line,
the second system backs off wherever the first one already drew a line.

**Line thickness changes naturally.** Outlines get thinner on flat surfaces and thicker
around sharp creases, based on the curve of the surface and distance from camera, similar
to how a hand-drawn line naturally varies in weight. This detail alone makes a big
difference in making it look "drawn" rather than just "shaded."

**Textured-looking shadows.** Inside dark/shadowed areas, the game blends in a subtle
hand-drawn-style hatching texture, different weights and slight randomness so it doesn't
look mechanical, angled off the normal grid, and broken up with noise so it doesn't
repeat obviously. It's meant to look like the texture of paper, not like a flat filter.

**Distance fog in steps, not a gradient.** Instead of the distance haze fading smoothly,
it's broken into four distinct levels. Far-away mountain ridges snap between these levels
instead of blending, so each ridge reads as a clean, flat shape stacked behind the one in
front of it, this is a common visual technique in hand-drawn animation. A smooth,
continuous fog would just turn those ridges into a blurry grey mess instead.

Other details: a sky with banded color and hard-edged cartoon clouds at two different
depths for parallax, sunbeams built as actual solid shapes (not a blurry glow effect),
banded reflections and highlights with hard edges, fake reflections using a flat 2D image
trick (no real reflection maps), a subtle glowing rim of light around riders and bikes, a
glow/bloom effect that stays sharp and graphic rather than soft and blurry, and color
grading (an overall color adjustment) generated from the same fixed palette.

## The mountain

The terrain is a 2048x2048 height map covering 4km of in-game world. It starts as layered
noise (some of it ridged to form sharp peaks, some smoother to form rolling foothills),
then gets run through a **water erosion simulation**, basically thousands of virtual
water droplets flow downhill and carve the terrain, the same way real rain and rivers
shape real mountains over time. Without this step, generated terrain just looks like lumpy
random noise, not like a real landscape. After that, a second pass settles loose rocky
slopes into a realistic angle, the way scree naturally settles on a real mountainside.

The race track isn't just placed on top of the finished terrain. Before the erosion
simulation even runs, the terrain is nudged to already have a rough, continuously
descending path built into it, so when erosion runs, it naturally carves realistic
gullies and ridges around that path instead of ignoring it. The specific features needed
for racing (jump ramps, a ravine, a narrow ridge, a stream) are then carved in precisely
*after* erosion finishes, because if they were added before, the erosion simulation would
fill them back in with sediment, which would obviously break the jumps and other course
features.

Different terrain surfaces (grass, dirt, rock, loose scree, snow) are placed automatically
based on height, steepness, and how eroded that area got, with clean, non-smooth borders
between each type of surface, similar to the "hard bands" style used everywhere else in
the visuals.

The terrain renders using a technique where the level of detail decreases the further it
is from the camera, snapped carefully so it doesn't visually "swim" or shift as the camera
moves, and blended so you don't see detail pop in or out.

## The track

3.3km long, one-way (start to finish, not a loop), dropping about 585 meters in altitude
total. Nine sections, each with its own feel:

1. **Technical start** - exposed rock, tight turns, uneven ground
2. **Scree run** - open and straight, build up speed on loose, low-grip ground
3. **Switchbacks** - six banked corners through trees, each one tighter than the last
4. **Rock garden** - a broken, diagonal rocky section that punishes a bad line choice
5. **Tabletop** - a clean, easy-to-read jump
6. **Ravine gap** - an actual 11.5 meter gap you have to clear
7. **Ridge sprint** - a narrow ridge with real drop-offs on both sides
8. **Stream bed** - dropping down onto wet rock
9. **Final sprint** - an open run to the finish line

The game includes checkpoints, split times, wrong-way detection, a preview indicator
before corners, and it saves a "ghost" replay of your best run.

## How the code is organized

```
src/
  core/        Game engine (runs physics at a fixed 120 times per second), input
               handling, math helpers, random number generation, noise generation
  npr/         Colors/palette, shader code, cartoon-style materials, outline
               generation, generated textures, sky, shadows, post-processing effects
  terrain/     Height map, erosion simulation, surface zones, level-of-detail terrain
               rendering, terrain materials, scattered objects, plants
  track/       Track path, track visuals, checkpoints, track-side objects
  bike/        Bike physics, wheels, bike model, trick system
  rider/       Character skeleton, character mesh, inverse kinematics (natural limb
               movement), character rig, poses
  ai/          AI-controlled riders, AI personalities, race management, player
               tracking, ghost replays, replay system
  fx/          Camera behavior, dust effects, speed effects, impact effects, debris
  hud/         On-screen display (canvas-based), UI widgets, menus, custom text
               rendering
  audio/       Sound engine, sound synthesis (generating sounds with code)
  game/        Core interfaces that everything else is built against, game constants,
               main game logic
tools/
  capture/     Automated tool for testing/reviewing the game visually
```

`src/game/Contracts.ts` defines the core rules/interfaces every other part of the game is
built against. Because every system (terrain, physics, characters, AI, camera, UI) was
built to follow those same shared rules, each part could be built somewhat independently
without needing to know the inner details of the others.

### Two important technical decisions

**Physics always runs at a fixed rate (120 times per second), no matter your frame rate.**
If a game's physics simulation runs faster or slower depending on your computer's
performance, the game's handling changes depending on the machine, which is a serious
problem for a racing game specifically. So physics always runs at the same fixed rate, and
the game smooths out what you see on screen between those physics updates. There's also a
safety limit: if your browser tab is minimized or paused for a few seconds, the game won't
try to "catch up" by suddenly running hundreds of physics steps at once when you come
back, it just skips ahead instead, to avoid a big stutter.

**Screen quality adjusts automatically to maintain performance.** The game watches your
recent frame rate and gradually adjusts rendering quality up or down to try to keep things
smooth. It reacts quickly if performance drops, but increases quality slowly, so quality
doesn't rapidly flicker up and down.

## Automated visual testing

```bash
npm run capture:install          # one-time setup
node tools/capture/capture.mjs --all
```

This runs the game in an automated browser in the background, controls time manually
(stepping the simulation forward by a fixed amount each time), and takes screenshots. This
means the exact same sequence of screenshots is produced every time, regardless of how
fast or slow the computer running it is, which matters because otherwise you couldn't
fairly compare two different versions of the game.

It can produce:

- high-resolution screenshots at specific game moments
- sequences of screenshots over time
- **contact sheets** - a single image showing a grid of frames from a sequence, side by
  side, so you can actually review motion and animation at a glance
- optional video clips

Screenshots are used to check things like composition, line quality, and color. Sequences
are used to check animation quality, how camera movement feels, and whether the game
actually feels fast during high-speed moments.

## Performance

Target: a steady 60 frames per second at high resolution on a fast modern computer/browser,
with no stutters during jumps or crashes.

- Efficient terrain rendering with level-of-detail blending
- All repeated objects (plants, rocks, dust, debris, wheel spokes) rendered efficiently
  using instancing (drawing many copies of an object efficiently)
- Objects outside the camera's view aren't rendered, and distant objects fade in/out
  smoothly instead of popping
- Screen resolution automatically adjusts to maintain smooth performance
- The on-screen display only redraws the parts that actually changed, not the whole
  screen, to save performance
- The physics, animation, and particle systems are written to avoid creating unnecessary
  new objects during gameplay, which helps prevent stutters caused by memory cleanup

Press **`` ` ``** in-game to see a performance overlay showing frame time, number of draw
calls, triangle count, physics steps, and current render quality.
